# Проксирование приложений на macOS

На macOS singctl работает иначе, чем на Linux. Эта страница объясняет почему и
даёт готовые копипаст-рецепты — в первую очередь для Chromium/Electron-приложений
вроде Cursor, VS Code, Chrome, Brave и Zen.

## Установка как системный инструмент (LaunchDaemon)

`make install` собирает бинарь и ставит `singctl` как **системную команду** в
`/usr/local/bin` (он в стандартном `PATH` macOS — дальше зовётся просто `singctl`),
плюс LaunchDaemon, который поднимает системный VPN при загрузке:

```
make install               # сборка + установка команды singctl + LaunchDaemon
```

Запускайте **без** `sudo` (`sudo make` не нужен и не используется). Сборка идёт от
вашего пользователя, чтобы не оставлять root-овых файлов; права root нужны только
для копирования в системные пути, поэтому установщик — по схеме как у Homebrew —
**один раз** запрашивает пароль (`sudo -v`) и под ним выполняет только привилегированные
шаги (`install` в `/usr/local/bin` и `/Library/LaunchDaemons`, `launchctl`).

`/usr/bin` намеренно не используется: он защищён SIP и доступен только для чтения;
правильное место для пользовательских команд на macOS — `/usr/local/bin`.

Перед первым включением **сохраните ключ один раз** интерактивно — демон берёт
его из сохранённого профиля (`~/.config/singctl`), а не из командной строки:

```
sudo singctl               # раздел «Ключи» → добавить ключ → выйти
```

Управление и удаление:

```
launchctl list | grep singctl     # загружен ли демон
sudo singctl --status             # статус
sudo singctl --attach             # живой лог
sudo singctl --stop               # остановить инстанс
tail -f /var/log/singctl.log      # лог демона
make uninstall                    # удалить бинарь + LaunchDaemon (сам поднимет sudo)
```

**Что это даёт и чего НЕ даёт.** LaunchDaemon — это **системный VPN на весь
трафик** (режим TUN), а не пер-процессный перехват в стиле Proxifier. Завернуть
конкретное приложение по-прежнему можно только запуском/перезапуском его через
прокси (см. ниже). Настоящий перехват уже запущенных приложений по процессу
требует подписанного Network Extension (Apple Developer ID, нотаризация,
согласие пользователя) и несовместим с расширением Cisco — это отдельный крупный
проект, в singctl он не реализован.

## Почему macOS отличается

- **Нет per-PID перехвата в ядре.** Маршрутизация трафика отдельного процесса
  через cgroup v2 + nftables fwmark — это возможность только Linux. На macOS
  такого механизма нет, поэтому «направить уже запущенное приложение в прокси»
  на самом деле означает **перезапустить** его с прокси-окружением (см. ниже про
  `--restart-pid`).
- **Проксирование = перезапуск.** Единственный способ завернуть приложение в
  прокси на macOS — стартовать его заново с нужными переменными окружения (или с
  флагом `--proxy-server` для Chromium). Поэтому в TUI для уже запущенного PID
  доступен только перезапуск, а не «горячее» подключение.
- **Socket-фильтр Cisco выше таблицы маршрутов.** Cisco Secure Client
  (AnyConnect) фильтрует соединения на уровне сокетов — **выше** таблицы
  маршрутизации, до того как пакет вообще доходит до маршрутов. Поэтому singctl
  не может «перебить» Cisco маршрутами. Сосуществование здесь — **только
  наблюдение**: singctl уступает (suspend) на время подключения/работы Cisco и
  возобновляется после его отключения, но никогда не трогает его сокеты или
  маршруты.

## Запуск приложения через прокси

В TUI: раздел **Приложения** (`x`) → поле **«Запустить приложение в прокси»** →
введите имя или команду → Enter.

Из CLI:

```
singctl --launch -- <app> [аргументы...]
```

Имена приложений резолвятся из `/Applications` (а также `/System/Applications` и
`~/Applications`), поэтому короткое имя работает: например `zen` найдёт
`/Applications/Zen.app` и запустит его бинарник внутри бандла.

singctl выставляет дочернему процессу такие переменные окружения (в обоих
регистрах — инструменты расходятся в том, какой читают):

```
HTTP_PROXY  = http://127.0.0.1:2080
HTTPS_PROXY = http://127.0.0.1:2080
ALL_PROXY   = socks5h://127.0.0.1:1080
http_proxy  = http://127.0.0.1:2080
https_proxy = http://127.0.0.1:2080
all_proxy   = socks5h://127.0.0.1:1080
```

`ALL_PROXY` использует схему `socks5h` (с `h`), чтобы DNS-резолвинг тоже шёл
через прокси удалённо, а не локально.

**Дочерние процессы.** Все процессы, которые запущенное приложение форкает,
**наследуют это окружение** (и флаг `--proxy-server` для Chromium), поэтому форки
тоже идут через прокси. Ограничение остаётся прежним: хелперы, запущенные
приложением **до** проксирования, перехватить нельзя — поможет только перезапуск
самого приложения (`--restart-pid` / `^R`), после которого новые форки наследуют
прокси. На Linux таких ограничений нет: cgroup захватывает и уже запущенные
дочерние процессы, и будущие форки.

## Chromium / Electron (Cursor, VS Code, Chrome, Brave, Zen)

**Chromium- и Electron-приложения ИГНОРИРУЮТ `HTTP_PROXY`/`HTTPS_PROXY`/
`ALL_PROXY`.** Одних только переменных окружения недостаточно — нужен флаг
запуска `--proxy-server`.

Копипаст-рецепт для Cursor:

```
Cursor --proxy-server=socks5://127.0.0.1:1080
```

или полный путь к бинарнику внутри бандла:

```
/Applications/Cursor.app/Contents/MacOS/Cursor --proxy-server="socks5://127.0.0.1:1080"
```

То же самое для остальных: `Code`, `Google Chrome`, `Brave Browser`, `Zen` и
прочих Chromium-приложений — подставьте имя/путь и тот же флаг.

**singctl делает это автоматически (smart preset).** Если вы запускаете известное
Chromium/Electron-приложение через поле «Запустить приложение» или
`singctl --launch -- <app>`, singctl сам добавит
`--proxy-server=socks5://127.0.0.1:1080`, если вы не указали `--proxy-server`
вручную. Известные имена: `cursor`, `code`, `vscode`, `chrome`, `chromium`,
`brave`, `zen`, `electron`, `slack`, `discord`. Свой `--proxy-server` всегда имеет
приоритет — singctl его не перетирает.

### DNS через прокси (`--host-resolver-rules`)

Флаг `--proxy-server=socks5://...` отправляет TCP-трафик в прокси, но Chromium
по умолчанию может резолвить DNS-имена **локально**, в обход прокси. Чтобы DNS
тоже шёл через прокси (важно для корпоративных внутренних доменов), добавьте:

```
Cursor --proxy-server=socks5://127.0.0.1:1080 \
       --host-resolver-rules="MAP * ~NOTFOUND , EXCLUDE 127.0.0.1"
```

Так Chromium перестаёт резолвить имена сам и отдаёт их SOCKS-прокси (аналог
`socks5h`).

## Ограничение `--restart-pid`

Перезапуск уже запущенного процесса в прокси-режиме (`--restart-pid` или `^R` в
процесс-пикере) восстанавливает командную строку через `ps`. Это **best-effort**:

- Кавычки и точное разбиение аргументов при восстановлении **теряются** — argv
  собирается из вывода `ps` по пробелам.
- Хорошо подходит для **CLI-процессов** с простыми аргументами.
- Для **GUI-приложений** перезапуск теряет состояние окна (открытые вкладки,
  позиция, несохранённый контекст). Если важно состояние — закройте приложение
  штатно и запустите заново через «Запустить приложение».

## GUI-как-root и `SUDO_USER`

singctl должен работать под `sudo` (для TUN-устройства и управления маршрутами),
но GUI-приложения вроде Zen или Cursor **отказываются стартовать от root**.
Поэтому singctl, запущенный под `sudo`, **сбрасывает права запускаемых дочерних
процессов на реального пользователя** (через `SUDO_USER`). Благодаря этому
проксируемое приложение стартует от вашего обычного пользователя, а не от root, и
запускается корректно.

Запускайте singctl через `sudo` (а не из root-сессии напрямую), чтобы `SUDO_USER`
был выставлен и сброс прав сработал.

## Проверка, что трафик идёт через прокси

После запуска приложения посмотрите два места в TUI:

- **Консоль приложений** — собственные логи (stdout/stderr) запущенного
  приложения, помеченные `[app pid]`. Здесь видно, что приложение стартовало и не
  падает с ошибкой прокси.
- **Соединения** — живой трафик приложения через прокси-цепочку: исходный
  процесс, source ip:port, полный destination host/ip:port, сеть и outbound-цепочка.
  Если соединения приложения там появляются — оно действительно ходит через
  прокси.

Если в «Соединениях» пусто, а приложение явно ходит в сеть — скорее всего это
Chromium/Electron без флага `--proxy-server` (см. раздел выше).
