# Проксирование приложений на macOS

На macOS singctl изолирует трафик отдельных приложений через **системное
расширение** (`NETransparentProxyProvider`) — в отличие от Linux, где это делается
бесплатно через cgroup/nftables. Эта страница объясняет модель и как ей
пользоваться. Установка и подпись Apple-модулей выполняются скриптом сборки.

## Установка как системный инструмент (LaunchDaemon)

`make install` собирает бинарь и ставит `singctl` как **системную команду** в
`/usr/local/bin` (он в стандартном `PATH` macOS — дальше зовётся просто `singctl`),
плюс LaunchDaemon, который поднимает системный VPN при загрузке:

```
make install               # сборка + установка команды singctl + LaunchDaemon
```

Запускайте **без** `sudo` (`sudo make` не нужен и не используется). Сборка идёт от
вашего пользователя, чтобы не оставлять root-овых файлов; права root нужны только
для копирования в системные пути, поэтому установщик — по схеме как у Homebrew —
**один раз** запрашивает пароль (`sudo -v`) и под ним выполняет только привилегированные
шаги (`install` в `/usr/local/bin` и `/Library/LaunchDaemons`, `launchctl`).

`/usr/bin` намеренно не используется: он защищён SIP и доступен только для чтения;
правильное место для пользовательских команд на macOS — `/usr/local/bin`.

Перед первым включением **сохраните ключ один раз** интерактивно — демон берёт
его из сохранённого профиля (`~/.config/singctl`), а не из командной строки:

```
sudo singctl               # раздел «Ключи» → добавить ключ → выйти
```

Управление и удаление:

```
launchctl list | grep singctl     # загружен ли демон
sudo singctl --status             # статус
sudo singctl --attach             # живой лог
sudo singctl --stop               # остановить инстанс
tail -f /var/log/singctl.log      # лог демона
make uninstall                    # удалить бинарь + LaunchDaemon (сам поднимет sudo)
```

## Две модели: системный VPN vs изоляция приложения

- **Системный VPN (режим TUN, клавиша `v`)** — заворачивает **весь** трафик
  машины. Не требует Apple-расширения, работает сразу. Используйте, когда нужно
  завернуть всё.
- **Изоляция приложения (per-app)** — заворачивает трафик **только выбранных
  приложений**, остальное идёт напрямую. На macOS это делает **системное
  расширение** (см. ниже). На Linux — cgroup/nftables (бесплатно).

## Per-app на macOS = системное расширение

Завернуть отдельное приложение на macOS, не трогая остальной трафик, можно только
через подписанное **System Extension** (`NETransparentProxyProvider`). Оно
перехватывает трафик на сетевом уровне по **bundle ID** приложения, поэтому ловит
**весь его стек** — Chromium/UI, Node/undici (extension-host Cursor/VS Code),
raw-сокеты — и автоматически покрывает все форки и хелперы (они наследуют signing
identity родителя). Никаких env-переменных, флагов `--proxy-server` или
перезапуска приложения не требуется.

Что для этого нужно (разово):

1. Собрать и подписать нативное macOS-приложение (`macos/Singctl/`), которое
   хостит встроенное расширение: `make app-macos DEVELOPMENT_TEAM=<TEAM_ID>`.
2. Запустить `Singctl.app` и **одобрить** расширение в System Settings →
   General → Login Items & Extensions.
3. Полную последовательность (Apple Developer Program, App IDs, capabilities,
   нотаризация и подпись CLI выполняются штатными инструментами Xcode.

Проверить, что расширение активно: `systemextensionsctl list` —
`com.singctl.proxy.netext` должно быть `[activated enabled]`.

## Как пользоваться

В TUI: раздел **Приложения** (`x`).
- **«Запустить приложение в прокси»** — запускает приложение и включает его захват.
- **Пикер процессов** — выберите уже запущенное приложение и заверните его (захват
  включается сразу, перезапуск не нужен).
- **«Проксируются сейчас»** — список изолированных приложений; `u` — снять захват,
  `k` — завершить процесс.

Из CLI: `singctl --launch -- <app>` (запуск+захват), `--route-pid <pid>` (захват
запущенного).

Если расширение не установлено/не одобрено, эти действия вернут понятную ошибку со
ссылкой на сборку (`make app-macos`).

## Сосуществование с Cisco

Cisco Secure Client (AnyConnect) фильтрует соединения на уровне сокетов — **выше**
таблицы маршрутизации. singctl с ним **только сосуществует**: уступает (suspend)
на время подключения/работы Cisco и возобновляется после отключения, никогда не
трогая его сокеты или маршруты. Расширение при этом продолжает перехватывать
выбранные приложения при активном Cisco — сосуществованием управляет слой политики
singctl (`internal/policy`), приостанавливая и возобновляя прокси-ядро, а трафик
прокси едет через маршрут по умолчанию.

## Проверка, что трафик идёт через прокси

- **Соединения** (TUI) — живой трафик через прокси-цепочку: исходный процесс,
  source/destination ip:port, сеть и outbound-цепочка. Если соединения приложения
  там появляются — оно ходит через прокси.
- Адресная проверка по процессу:
  ```
  lsof -nP -p <PID приложения> -i
  ```
  Соединения должны идти на `127.0.0.1:1080` (локальный SOCKS singctl), а не
  напрямую во внешний AWS/Cloudflare. Поскольку расширение захватывает по bundle
  ID, это верно и для extension-host/хелперов приложения.
